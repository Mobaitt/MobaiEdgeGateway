# 边缘网关采集容量与性能优化方案

日期：2026-09-08
状态：待实施。本文件是设计与验收方案，不代表功能已经实现或容量已经实测达标。

## 1. 目标与范围

在现有单进程架构上，提高采集正确性、周期稳定性和输出吞吐，隔离慢设备、慢发送通道及慢 WebSocket 客户端。

第一轮优化覆盖 Modbus 读取计划、运行指标、发送通道队列和 WebSocket 连接队列；后续根据压测结果优化快照、规则与虚拟点。暂不引入微服务、消息中间件或更换数据库。

遵循已确认行为：

- WebSocket 通过 `/ws?topic=device` 订阅；实际 topic 对应通道配置。
- 暂不增加鉴权。
- 保留采集失败时上一份有效快照的既定语义；性能优化不能静默改变质量、时间戳及过期处理规则。
- 默认保持现有全量推送格式。增量模式必须显式启用并定义客户端同步机制。

## 2. 容量定义与现有证据

此前后端 21 项测试通过，并在少量 Simulator 点位下验证了 HTTP 和 WebSocket 输出。这只能证明相应功能链路可运行，不能证明千点或万点容量。前端生产构建和真实 Modbus 设备容量尚未完成验证。

容量报告必须同时包含：物理点数、虚拟点数、设备数、采集周期、寄存器分布、请求响应耗时、规则数量、发送通道数、订阅连接数及硬件环境。

计算口径：

- 每秒更新量 = 各采集组的点位数 / 周期秒数之和。
- 单设备一轮耗时约为各串行请求耗时之和，加上解析、规则和快照更新时间。
- 出站吞吐约为各输出的单包字节数 × 每秒发送次数 × 接收端数量之和。
- 总点数相同，不代表请求数、CPU 开销或带宽相同。

以单寄存器点、单从站、同功能码、单请求耗时 10ms 为假设：1,000 个连续点正确分包后约需 8 次请求，纯通信约 80ms；若离散到逐点请求，则约需 10 秒。这是解释容量差异的模型，不是实测承诺。

阶梯目标为 1,000、5,000、10,000 个物理点，分别验证 1 秒和 5 秒周期。10,000 点/秒是待验证目标，不是当前产品规格。

## 3. 第一阶段：正确读取与可观测性

### 3.1 Modbus 读取计划

主要文件：`EdgeGateway.Infrastructure/Strategies/Collection/ModbusCollectionStrategy.cs`。

当前实现每轮分组、排序和合并连续地址，但合并长度没有请求上限；连接探测固定读取从站 1 地址 0，非法地址会返回 0。

实施内容：

1. 初始化或配置变更时构建不可变读取计划，按从站、功能码、地址排序，预计算请求区间和点位偏移。
2. FC03/FC04 每次不超过 125 个寄存器；设备允许的更低上限优先。位读取按对应功能码限制和设备能力处理，不能沿用寄存器点宽度。
3. 多寄存器点尽量完整放入一个请求；单点宽度超限或区间越界时拒绝配置并明确报错。
4. 解析使用实际地址偏移，覆盖重复、重叠、非连续点，不能仅累加点宽度推算偏移。
5. 默认只合并连续可读区间。跨间隙合并作为后续可选能力，限定间隙长度，并在非法地址响应时回退拆分，避免反复试错。
6. 删除固定从站/地址探测，使用配置中的有效读取计划确认可读性；非法地址明确报错。明确原始偏移与 4xxxx 等地址表示约定，提供兼容校验，避免既有点位偏移发生隐式变化。
7. 明确请求级超时和每轮重试预算。取消等待必须能结束底层操作或关闭其连接，不能留下后台读取与下一轮竞争。
8. 保持同一连接上的请求串行，按设备或共享物理链路限制并发；不要对单个设备无限并行请求。

协议依据：https://modbus.org/docs/Modbus_Application_Protocol_V1_1b3.pdf

### 3.2 运行指标

主要文件：`EdgeGateway.Application/Services/DataCollectionService.cs`、设备运行状态存储及相关查询接口。

增加每轮请求数、读取耗时、成功/失败点数、超时次数、重连次数、周期超时次数和最后成功采集时间。调度耗时使用单调时钟；采样时间保留业务时间戳。

增加聚合耗时、规则耗时、虚拟点计算耗时、发送耗时、输出包大小和队列深度。指标按设备、通道聚合，避免逐点标签导致监控本身消耗大量内存。

日志使用周期汇总和重复错误限频；生产模式不输出每点值和高频 SQL。保留完整故障计数。

验收：覆盖 124/125/126 寄存器边界、跨包多寄存器点、重复/重叠地址、非法地址、取消、超时及断线重连；比较预期点值与实际解码值。先建立优化前后的同条件基线，再报告收益。

## 4. 第二阶段：发送隔离与有界积压

### 4.1 每通道独立发送

主要文件：`EdgeGateway.Application/Services/DataSendService.cs`。

当前聚合等待全部通道完成，发送期间持有全局生命周期锁。一个慢通道会拖长下一轮聚合及配置操作等待时间。

改为：聚合生成稳定批次 → 投递各通道有界队列 → 各通道独立消费者发送。

- 队列元素使用不可变批次或稳定副本，不引用随后还会被修改的容器。
- 初始实时快照队列容量建议为 1，消费者持有当前发送包，待发区保留最新快照；记录合并次数和批次序号。
- 合并策略只适用于实时状态。命令、事件及必须逐条保留的数据不能进入可覆盖队列；可靠交付需要独立设计持久化、重试及磁盘容量策略。
- 为每通道定义超时、退避重试和故障状态，落实并发预算。不能仅改为无上限 Task.Run。
- 通道停用/更新按通道协调：停止接收旧版本批次、取消或限时完成在途发送、释放旧策略、启动新版本。其他通道持续运行。
- 避免全局锁覆盖网络 I/O；保留配置版本与释放安全性，不能简单删除锁。
- 停机采用有时间上限的收尾，超时后取消，报告未发批次数。

验收：注入慢 HTTP、断开的 MQTT 及持续发送失败，确认健康通道仍按期输出，队列内存有界，通道启停更新不会复活旧策略或重复发送旧配置批次。

### 4.2 WebSocket 客户端隔离

主要文件：`EdgeGateway.Infrastructure/WebSocket/WebSocketConnectionManager.cs`、`WebSocketServerMiddleware.cs`。

- 每个连接一个发送消费者，数据、心跳及响应都经过串行发送，避免同一 Socket 并发写。
- 实时数据设最新快照待发槽；控制消息使用独立有界队列或等效优先级机制，不被快照覆盖。
- 设置发送超时、连续失败阈值及关闭握手超时；覆盖主动关闭、CloseReceived、异常中断和服务停机。
- 同主题同批次复用一次 UTF-8 编码；缓冲区在所有使用者完成前不能归还或修改。
- 按主题维护连接索引；切换订阅和断开时同步维护，避免索引残留。
- 保持 `/ws?topic=...` 和已有订阅校验行为。接收消息增加长度上限，避免无限累积碎片。

验收：正常客户端、慢接收客户端、突然断网客户端混合运行；验证健康连接延迟、队列上限、消息完整性、心跳并发、动态订阅与完整关闭握手。

## 5. 第三阶段：按实测热点降低开销

### 5.1 快照与通道映射

配置变更时缓存映射数组及元数据；减少每轮 LINQ、临时列表、占位对象和字典重建。按设备建立查询索引，保证删除/停用/重载时一致更新。使用稳定批次保证跨线程数据一致性，不承诺不同设备具有同一物理采样时刻。

默认全量推送保持兼容。可选增量模式需规定：首次订阅全量、值/质量/状态变化判定、批次序号、断线恢复、定期全量以及点位删除通知。浮点死区单独配置；统计合并量，不能把少发包误报为更多成功采集。

### 5.2 规则与虚拟点

将同步阻塞异步回调改为可等待的批处理接口，保留每设备顺序及规则拒绝语义。无规则时使用快速路径；缓存解析结果、参数化表达式，并验证缓存对象线程安全。

虚拟点建立依赖图及拓扑顺序，检测循环依赖。根据依赖变更计算受影响节点；时间相关表达式继续定时执行。先分析 CPU 热点再决定并行度，避免为每个点创建任务。

验收：同一输入批次的规则和虚拟点结果与基线一致；覆盖文化区域数值格式、依赖缺失、循环依赖、虚拟点链以及失败时保留旧有效快照的既有行为。

## 6. 压测与验收方案

测试数据使用独立临时数据库、独立输出目录及本地模拟服务。不得使用现有 gateway.db 做写入压测。记录 Git 版本、配置和随机种子，测试完成后只清理本轮明确创建的资源。

### 6.1 场景矩阵

| 维度 | 场景 |
| --- | --- |
| 点位数 | 1,000 / 5,000 / 10,000，达标后再扩展 |
| 周期 | 1 秒 / 5 秒；100ms 作为独立高频实验 |
| 设备分布 | 总点数固定，分散到 1 / 10 / 100 台模拟设备 |
| 协议 | Simulator 测软件处理；本地 Modbus TCP 模拟服务测协议链路 |
| 地址布局 | 连续、离散、多从站、多功能码、多寄存器点 |
| 响应时间 | 5 / 20 / 100ms；另注入超时和断线 |
| 规则/虚拟点 | 无规则、代表性简单规则、复杂表达式及依赖链 |
| 输出 | HTTP / MQTT / WebSocket，单通道及混合多通道 |
| 订阅连接 | 1 / 10 / 50，混入慢连接 |
| 变更 | 通道启停、映射更新、订阅切换、设备重连 |

分三步运行，避免一开始穷举全部组合：无故障阶梯寻找拐点 → 拐点附近测试布局及负载组合 → 目标配置做故障注入和长稳。

每档先预热 5 分钟，再测量至少 30 分钟；最终目标配置持续 24 小时。真实现场设备另做抽样验证，本地模拟结果不能替代设备能力声明。

### 6.2 建议验收门槛

以下是目标，须在报告中明确测量环境和数据口径：

- 正常负载下，单轮处理耗时 P99 不超过配置周期的 80%，周期超时比例低于 1%。
- 无故障场景的成功采集比例不低于 99.9%；对测试输入逐点校验，无地址错位、解码错误或主题串发。
- 健康客户端端到端新鲜度 P99 不超过“采集周期 + 聚合周期 + 500ms”；新鲜度以采样时间计算，不用发送时间替代。
- 单通道/单客户端故障不使健康输出突破其延迟门槛。
- CPU 稳态均值以不超过 70% 为初始目标，记录 P95 和核心数；若达不到先报告瓶颈，不通过更换测试口径掩盖。
- 内存和队列不持续增长，记录托管堆、工作集、分配速率、GC 暂停和积压；24 小时后没有持续泄漏趋势。
- 重连、配置更新、停机均能在配置超时预算内结束，无遗留读取任务或旧策略竞争。

当前 1 秒聚合器包含发送耗时，优化前报告应记录实际聚合间隔，不仅记录配置值。

## 7. 交付与实施顺序

1. 基线与隔离测试工具：指标采集、独立数据库、本地协议模拟服务和可重复运行脚本。
2. Modbus 正确性与计划缓存：边界测试通过后对比请求数和轮询耗时。
3. 通道与连接隔离：验证慢下游、并发发送和生命周期行为。
4. 根据指标选择快照、表达式或序列化热点优化，不先做全面重写。
5. 输出容量报告：每种配置的达标档位、瓶颈、资源占用、延迟及失败比例；区分模拟、真实设备和未验证项。

每一步保持可独立回退。增量推送、跨间隙合并等改变行为的能力默认关闭；保持客户端数据格式兼容。涉及数据库结构变化时另列迁移、备份和回退步骤。

完成标准是可复现的容量证据与故障隔离效果，而不是单次启动成功或短时间收到数据。
